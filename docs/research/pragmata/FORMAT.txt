PRAGMATA PPSA02530: VERIFIED SAVE FORMAT NOTES
===========================================
Analysis scope: the 12 data*.bin files in PPSA02530_saves_dec.zip, checked
2026-10-27. No game executable or console was available. Any semantic label
not explicitly confirmed below is a hypothesis, not a proven game contract.

2. OUTER DSSS CONTAINER

All integers in this document are little-endian unless stated otherwise.
Let F = complete .bin file size.

File offset 0x00: 4 bytes ASCII "DSSS".
File offset 0x04: uint32 version = 2.
File offset 0x08: uint32 flags = 0x10 (Mandarin).
File offset 0x0c: 4 bytes observed zero padding.
File offset 0x10: first Mandarin block.
File offset F-0x8c: 0x80-byte key/RSA trailer, preserved unchanged by the tool.
File offset F-0x0c: uint64 exact decrypted payload length.
File offset F-0x04: uint32 MurmurHash3 x86-32 of bytes [0, F-4), seed 0xffffffff.

There is no DEFLATE compression flag in these files. The game payload remains
encrypted even though the ZIP name contains "dec". That name describes the
removed PS5 container encryption, not removal of Mandarin.

3. MANDARIN BLOCKS AND CHECKSUMS

Verified PS5 ID/key input: 526253637 (0x1f5dfe45).
Verified PRAGMATA encryption PRNG seed: 0x7da24a9e1479f3d7.
The upstream RSA generation seed is 0x3f90d767f13abe2e; this tool preserves
the existing trailer and does not need to generate a new one.

Each block:
  +0x000..+0x1ff: four 128-byte ElGamal-style key/IV metadata pairs.
  +0x200..+0x207: uint64 CityHash64 of the valid plaintext bytes in this block.
  +0x208..+0x20f: 8 unknown metadata bytes, preserved.
  +0x210 onward: AES-128-OFB ciphertext.

The entire first 0x210 metadata bytes are XOR-masked with generated PRNG bytes.
AES keys and IVs are derived deterministically from the same PRNG and key input.
Block ciphertext capacities vary from 1 to 8 multiples of 0x4000 bytes.
The last block can contain unused capacity; preserve it when making edits.

Exact sequence:
  N = ceil(plaintext_length / 0x4000).
  Start state = encryption seed.
  Generate ALL N potential block sizes first:
    capacity[i] = ((state & 7) + 1) * 0x4000;
    state = mix(state + 0x9e3779b97f4a7c15), modulo 2^64.
  Only enough of these capacities to cover plaintext_length become real blocks.
  Add bitwise NOT of the 64-bit key input to the final state, modulo 2^64.
  For each real block, take 16 next-state outputs; the low byte is an AES key
  byte and the next byte is an IV byte. Then take 0x210 further outputs for
  metadata XOR-mask bytes. Continue with the next block.

mix(z):
  z = (z XOR (z >> 30)) * 0xbf58476d1ce4e5b9 modulo 2^64
  z = (z XOR (z >> 27)) * 0x94d049bb133111eb modulo 2^64
  return z XOR (z >> 31)

Important: the MIXED OUTPUT is assigned back as the next state. Treating
this as a conventional SplitMix64 state progression produces wrong keys.

For a size-preserving edit, AES-OFB allows:
  new_ciphertext = old_ciphertext XOR old_plaintext XOR new_plaintext
Then update the masked CityHash64 of each changed block and the outer Murmur3.
No new key/IV, ElGamal pairs or RSA trailer are needed when the layout and key
remain unchanged. This avoids re-creating unknown metadata and padding.

4. DECRYPTED SERIALIZATION

The plaintext is a typed, hash-addressed class stream, not JSON, SQLite,
Unreal GVAS or an ordinary list of fixed offsets.

Root record:
  uint32 native/root field hash
  uint32 field count
  uint32 class/type hash
  repeated fields

Field:
  uint32 field-name hash
  int32 type tag
  type-specific payload
  align to 4 bytes after the field

Primitive payload: uint32 byte size, alignment, then the primitive bytes.
Class payload: uint32 field count, uint32 class hash, repeated fields.
String payload: uint32 UTF-16 code-unit count, followed by UTF-16LE bytes.
Strings are counted, not necessarily zero-terminated.
Struct payload: uint32 byte size, alignment, then opaque bytes.

Array payload:
  int32 member type
  uint32 member size
  uint32 element count
  int32 array type (0=value elements, 1=class elements)
  optional uint32 marker 0xffeeffee and element_count uint32 hashes
  elements, followed by alignment to 4
The optional marker/hash list applies to class arrays. Class elements carry
their own field-count/class-hash records, not ordinary per-element field headers.

Type tags:
  -1 array; 0 unknown/unsupported; 1 enum; 2 bool;
   3 int8; 4 uint8; 5 int16; 6 uint16; 7 int32; 8 uint32;
   9 int64; 10 uint64; 11 float32; 12 float64;
  13 char8; 14 char16; 15 UTF-16 string; 16 struct; 17 class.

Field-name hashes match MurmurHash3 x86-32 over UTF-8 names with seed
0xffffffff. Confirmed type-name matches are listed in verified_save_map.json.

CRITICAL ALIGNMENT FINDING
The serializer aligns its original cursor INCLUDING the 16-byte DSSS header.
When parsing a headerless plaintext dump, retain origin = 16:

  absolute = plaintext_offset + 16
  aligned = ((absolute + size - 1) & ~(size - 1)) - 16

This deliberately reproduces the observed bit-mask rule even for struct sizes
such as 24. It is not interchangeable with generic rounding to a multiple of
size, or with simply aligning plaintext_offset itself.

The earlier attached transcript's parser used origin 0. It stopped partway
through slots 2, 4, 6, 8 and 10 when it encountered affected structs. With
origin 16, every supplied file parses exactly to the declared payload length.
The attached JSON summaries are numerically useful, but were not a complete
reproducible format specification.

9. EDITOR IMPLEMENTATION STRATEGY

1. Validate DSSS version/flags and outer MurmurHash3.
2. Read exact plaintext length; derive block layout, keys and metadata masks.
3. Decrypt with AES-128-OFB; validate each block's CityHash64.
4. Parse the typed tree with alignment origin 16; require complete consumption.
5. Locate inventory by class 3a83076c, then _InventoryItems and an existing _ID.
6. Patch the fixed-size int32 _Quantity value in the original plaintext bytes.
7. Apply the OFB XOR delta to the corresponding ciphertext bytes, update the
   affected masked CityHash64 value(s), then the outer MurmurHash3.
8. Re-decrypt and re-parse the output before writing it as a separate file.

Preserve unknown fields, padding, block metadata and the RSA trailer.
Do not resize arrays, reorder sections, regenerate the whole object tree or
copy offsets from one slot into another for a first implementation.

For user-friendly item names, obtain a matching game-data ID dictionary or
compare controlled in-game before/after saves changing one known item only.
For console validation, first try an unchanged roundtrip restore, then one
small legal quantity change in a spare slot.
