## Summary

The `insomniac` 0.2.0 plugin is a useful read-only Rift Apart campaign inspector, with validated DAT1 framing and named root DDL fields, but no weapon inventory, armor management or location-resolved completion view. A much better editor would show named weapons and their upgrade trees, cosmetic armor separately from earned bonuses, collectible checklists by planet, and carefully validated resource controls. There is immediate value available without writing: quick-select weapon paths and nine additional gameplay DDL roots are present in the PS5 corpus and can support richer read-only views. The top three blockers are **unestablished save-integrity/write acceptance**, **undecoded inventory and dependent gameplay state**, and **missing PS5-validated joins from save identities to versioned game data and collectible locations**. Framework work is primarily about presenting and supplying reference data safely; existing scalar specs, lazy sections, multi-file output and undo already support much of the first implementation.

### Integrity / crypto

- **Verified:** outer PS5 decryption has already occurred; supported DAT1/DDL is readable without adding an AES layer or compression. Neither that fact nor low entropy proves every opaque section is plaintext or checksum-free. No inner key/signature material was found or required for these reads.
- **Identifier versus integrity:** [Rivet DDL reader](https://github.com/neptuwunium/rivet/blob/a631c96ed6455f9873a646825d37883f99defa6e/Rivet.DDL/DDLSerializer.cs) and local `DdlReader.cs` distinguish name identifiers from serialized strings containing two hash words. The seeded name CRC matches sample descriptors; this is not a whole-save integrity result. Numeric patches can preserve strings, but changing quick-select paths requires establishing their string hash/checksum rules and padding; fixed character count alone is insufficient. EUPL upstream implementation remains reference only.
- **Existing negative scan:** `plugins/Insomniac/research/{inspect_integrity.py,hash_algorithms.py}` and `RESEARCH.md` report 41,652 CRC32/CRC64/FNV/Murmur section candidates across 36 primary saves, with no nondegenerate outside-range matches. Not rerun in this round. It tests limited coverage/seeds and does not rule out zeroed checksum fields, custom seeds, whole-file/cross-section coverage, larger hashes or signatures. Fresh verification confirms `BC60B495` tracks XP, not a discovered digest.
- **Patch databases:** current pinned heads of [Apollo patches `273f032b4c31c017fed5c1588f209b8faf87ba6c`](https://github.com/bucanero/apollo-patches/tree/273f032b4c31c017fed5c1588f209b8faf87ba6c) and [SaveWizard-Resources `4c32596efde54af7bec390b298265f09c929d94d`](https://github.com/sterben-Dev10/SaveWizard-Resources/tree/4c32596efde54af7bec390b298265f09c929d94d) match the earlier README research. Fresh tree-name queries found no Rift/PPSA01474 path; the earlier plugin research also searched contents. Both **GPL-3.0**, no code port proposed. Absence from these databases does not establish integrity-free writes, and older PS3/PS4 checksum repair is not transferable evidence.
- **Required experiment:** compare unmodified export, one legal fixed-width bolt increment, and one existing gold-bolt-option toggle separately on owner-controlled PS5 saves, with game/build/HUD observations and subsequent re-save/reimport. First establish a baseline in a private research harness; do not enable a UI “force save” bypass. If a change is rejected, distinguish malformed serialization, mirrored state, game-rule dependencies and actual integrity failures before guessing a checksum. Broaden hash hypotheses only when a changing byte range supplies evidence. No such console experiment occurred here.

## Vision

- **Overview / character:** campaign and slot identity, character, play time, verified wallet, health/XP once identified, challenge-mode state, and a clear supported-build/read-only reason. Keep career totals separately labeled. Display unknown values without silently coercing them to a valid range.
- **Arsenal / loadout:** searchable named weapons with optional local icons and short descriptions, owned/available status, four quick-select slots, per-weapon XP/level/ammo, base/upgraded/Omega variants and an upgrade grid showing costs/prerequisites. Initial release shows the four stored path references even before full inventory support. Generic stack controls apply only to truly stackable items.
- **Armor:** collected sets/pieces, head/chest/legs cosmetic slots, color choices, and separately explained permanent collection bonuses. Show missing assets/entitlements honestly; selecting an appearance must not fabricate collection bonuses or DLC ownership.
- **World / collectibles:** planet-grouped gold-bolt and spybot checklists with unresolved IDs visible; add Lorbs, CraiggerBears, Zurpstones, pocket dimensions, arena and Glitch progress when mappings are established. Show quest states read-only before any completion controls. A calibrated map links a marker to its checklist entry, with a text-table alternative.
- **Validated actions:** choose a bounded resource target; refill owned weapons within computed ammo caps; apply a loadout preset using owned items; later purchase eligible upgrades as a consistent transaction. Every action previews affected records, costs and dependent state, supports one-step undo where promised, and never advertises “max everything” over unknown fields. Keep raw trees/hex available as bounded diagnostics.

## Phased plan

**Phase 1 — richer read-only editor immediately (M).**

- [ ] Extend root decoding by section strategy, including the observed +4/+8 prefixes; retain current byte preservation and limits. Present preferences, quick-select paths and additional campaign flags/counters in useful groups.
- [ ] Add a small, source-tagged weapon-path dictionary only for established joins; unresolved internal names remain visible. Distinguish shortcuts from actual ownership.

- Evidence: current corpus already supports framing/path displays; HUD screenshots or extracted configs needed for names, units and difficulty labels. Risk: low for reads, medium for semantic overstatement; no editing enabled.

**Phase 2 — decode inventory and build meaningful world views (L).**

- [ ] Reverse-engineer `00D0A9DF` using the 27 `TVNI` anchors as candidates, proving atom bounds/versions/types rather than splitting blindly at magic bytes. Identify containers, item instances/config references, ownership, equipment and state payloads.
- [ ] Add bounded recursive DDL/map decoding with stable identities, recursion/node/value budgets and retained opaque spans. Decode objective, global, dimension, award and fog roots incrementally; do not expose every schema type eagerly.

- Evidence: INSOMNIAC-R1/R3/R6/R7; existing snapshots help corroborate changes but are not one-variable experiments. Risk: high for inventory identity and graph dependencies; read-only output is valuable even if editing stays blocked.

**Phase 3 — establish the write boundary and first scalar edits (M–L, research uncertainty).**

- [ ] Use a private research patcher that locates fields through descriptors and changes one existing scalar without changing serialized width. Preserve every unrelated byte and collect complete byte/semantic diffs.

- [ ] Validate independent legal edits to bolts and one existing option, including load, intended effect, re-save and reimport. XP edits must account for the observed XP mirror and any newly discovered dependencies.
- [ ] Promote only proven edit paths to Experimental after meaningful edit/reopen conformance; leave other fields read-only. Preferences need their own validation even if a gameplay edit succeeds.
- Evidence: INSOMNIAC-R1/R4; an owner-authorized existing editor output could accelerate diagnosis but is optional. Risk: potentially blocking unknown integrity or game constraints; no promised delivery date for a signature/key problem.

**Phase 4 — edit existing weapons, equipment and resources consistently (L).**

- [ ] Add per-weapon legal XP/level/ammo controls using verified config relations, purchased upgrades and normal/Omega mode. Never set an aggregate counter as a shortcut for individual progression.
- [ ] Allow only owned-item quick-select/equipment choices; correctly rewrite string identifiers/checksums if the format requires it. Resolve raritanium accounting before offering a wallet target or refund.
- [ ] Add collection-aware gold-bolt options, safe refill actions and owned-loadout presets. Preview costs/dependencies and return all primary/derived changes atomically for undo.
- [ ] Add icons, row inspectors, upgrade-grid visualization and calibrated read-only maps when reference packs permit; text remains fully functional without copyrighted assets.
- Evidence: Phase 2 identities + Phase 3 write proof, mode/boundary pairs and in-game tests per feature. Risk: medium–high, especially level-derived stats, passive armor bonuses and update variants.

**Phase 5 — conditional structural changes and advanced progression (L; explicit gate).**

- [ ] Consider granting a missing ordinary weapon/armor piece only after record construction, ownership, unlock/award state, string-pool changes, offsets and integrity are understood. Reuse a documented constructor/template policy, not copied foreign save records.
- [ ] Require structural undo snapshots, complete dependency preview and tests before add/remove or mass collectible completion. Defer these features if those guarantees are unavailable.
- [ ] Treat quests/checkpoints/arena completion and challenge-mode conversion as separate state-machine projects; prefer the game generating a new Challenge Mode slot. No blanket “finish story” action, paid-entitlement grants or new-path export assumptions.
- Evidence: absent/present pairs, mode transitions, independent campaigns/builds and console validation of downstream progression. Risk: highest; optional after the core editor is useful.

## Acceptance criteria

- [ ] Implementation stays inside `plugins/Insomniac/` under the current plugin rules; framework/UI changes are separately owned work described by requirement ID. Keep maintainable C# files under 300 lines where practical and below the 500-line hard limit; do not add plugin-local hooks/build tooling.
- [ ] Preserve every original record, duplicate ZIP generation, unknown section, field, string metadata and padding. No-op serialization is byte-identical across all 76 supplied game-file records, and remains so after expanding nested parsing.
- [ ] New root/recursive readers validate checked bounds, counts, field names, depth and total node/value budgets; corrupted/unsupported structures fail precisely or remain explicitly opaque without partial mutations.
- [ ] P1 exposes useful quick-select and preference data without claiming shortcuts imply ownership; unknown display joins, numeric menu codes and location indices remain labeled honestly.
- [ ] Inventory decoding proves framing/record identities and ownership across both campaigns; marker occurrence alone is never an item count. Weapon XP/level/ammo are independently identified rather than inferred from aggregate career XP.
- [ ] Every named item/quest/collectible join records its source/revision/build and sample or in-game evidence. Unknown hashes survive loading and export. Reference content has a recorded license route; the plugin performs no network/filesystem I/O.
- [ ] Any displayed wallet/raritanium, health, difficulty, planet mapping and mode-dependent limit is supported by a controlled observation. Preserve existing out-of-policy values for inspection; reject unsafe new edits instead of silently clamping a save on open.
- [ ] Initial edits target existing fields within their current serialized capacity. Any width promotion, string change, collection growth or relocation has its own proven serializer and integrity coverage before exposure.
- [ ] For every enabled edit, serialized output reparses, intended values survive re-open, all known mirrors/invariants update, unrelated bytes remain unchanged except documented integrity bytes, and undo restores the original. Multi-field failures are atomic.
- [ ] Resource/loadout/refill actions operate only on established identities and legal caps; complex actions provide a verified preview and transaction. No quest completion, blanket collectibles, missing-item grants or entitlement changes are enabled through unknown dependencies.
- [ ] Export preserves save-directory identity and backup policy; unequal backups and other generations are not overwritten by assumption. Re-opening our output is required but explicitly does not establish console acceptance.
- [ ] New tests cover meaningfully different writes, widths, empty collections, nested/map boundaries, corruption, unknown-ID preservation and mode transitions; private sample tests skip when absent. Run plugin conformance and appropriate framework checks during implementation, not this research task.
- [ ] UI tests verify visible lazy explorers, confidence/warnings in row details, search, keyboard access, missing-icon behavior and bounded views. Map coordinates align with at least three known non-collinear landmarks per supported transform; text navigation remains available.
- [ ] Record owner-observed successful PS5 load, intended effect, subsequent save/reimport and downstream gameplay for each edit family. Preserve ReadOnly until the write boundary is established; only a human promotes Stable.
- [ ] README documents precise supported features, integrity conclusions and remaining unknowns, pinned sources and per-file licensing. Never commit private saves, extracted game assets or account metadata.

## Open questions & risks

- Is there a save-body checksum at all, where is it covered, and do particular sections have independent integrity? Existing negative scans cannot answer this; no key/signature algorithm should be invented to explain an unperformed write test.
- What do the 27 inventory markers delimit, and which state belongs to Ratchet, Rivet, shared inventory, upgrades, cosmetics or unrelated systems? Confirm identity and ownership before naming item records.
- Why do lifetime raritanium spending and career totals differ? Potential bonuses/rewards/reset accounting must be measured, not corrected by assuming subtraction. A meaningful available balance may live in inventory state.
- What do string metadata hash words cover, how are asset paths normalized, and do PS5/PC versions use different string-versus-asset encodings? Current samples already disprove blindly using the PC class types as wire layouts.
- `CurrentLevel=0` across the supplied gameplay records prevents proving planet indices; checkpoint/dimension/objective data may hold the useful location identity instead. Missing/null schema fields and default-valued runtime properties need explicit handling.
- Collected gold-bolt hashes, RYNO bits, per-location counters, objective graphs and awards may duplicate one acquisition; changing only a visible count could leave rewards, progression or later saves inconsistent. Trophy state must not be inferred from an in-save counter alone.
- Equipment cosmetics and collected passive bonuses are distinct. DLC/preorder/anniversary differences, Omega upgrades and challenge resets can invalidate a universal catalog or “unlock all” recipe.
- Reference-tool licenses do not license Sony's data/icons. The useful CC0 schema sidecar reduces code/schema licensing friction but does not make game text, textures or maps CC0. Keep owner-supplied data packs private unless redistribution rights are established.
- Maps require verified world-to-image transforms, dimension variants and fog-bit ordering. A visually plausible overlay is insufficient evidence; defer precise maps when only guide screenshots are available.
- This corpus contains two campaigns and many related snapshots, not 36 independently documented playthroughs. No new builds/tests or in-game experiments were performed in this planning round; research findings must not be represented as edit compatibility.
