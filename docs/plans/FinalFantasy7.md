# FinalFantasy7 — improvement plan

## Summary

The `ff7r` plugin already preserves and explores the custom linked-record containers and edits gil, inventory quantities and materia AP for PS5 Remake Intergrade/INTERmission and retail Rebirth; the Rebirth demo remains read-only. A substantially better editor should provide named character sheets, inventory categories, owned-equipment and materia loadouts, and separate progress/collectible dashboards for each game. The strongest immediately usable research is the MIT Game Tools Collection schema and reference data, whose character and instance-reference layouts agree with meaningful values in our samples. The top three blockers are **controlled PS5 before/after saves plus console validation**, **unverified gameplay dependencies and item-specific limits**, and **a cleared source and delivery path for descriptions/icons together with richer UI controls**. Container decoding and an unknown mandatory encryption key are not the present blockers; richer writes must still preserve unknown data and prove their dependencies individually.

Common files and demo cannot edit. There is no implemented bulk action, character sheet, equipment-reference model, quest editor or custom asset provider.

- `.../ItemNames.cs`, `.../Resources/names.json`, `plugins/FinalFantasy7/THIRD-PARTY-NOTICES.txt`: names already exist: 337 item/54 materia mappings for Remake and 883/88 for Rebirth. These are variant-specific numeric type-ID dictionaries from MIT upstream, not complete descriptions, legal limits, instance metadata or icons. Unknown IDs retain raw identity. Do not spend Phase 1 recreating the name table.
- `.../SaveToolkit.Plugins.FinalFantasy7.Tests/{SampleFormatTests,ContainerTests,ExplorerTests,EditingTests,FinalFantasy7ConformanceTests}.cs` cover sample opening, byte-identical no-op output, malformed framing, bounded views, scalar edit scope and restoration. The README reports an earlier 45/45 plugin-test run, not a test run performed during this planning task. Existing AP edit coverage increments an already maxed two-star materia by one; it does not test crossing a star threshold, owner consistency or console behavior.
- Framework baseline: `src/SaveToolkit.Sdk/Views/ViewNode.cs` already has tabs, lazy sections, editable tables, actions, images and hex; `Values/FieldSpec.cs` has enums, descriptions, flags and scalar ranges. `ISaveDocument.cs` already supports sibling reads, multi-file outputs and `StructureChanged`. There is no item-reference/catalog spec, equipment-slot topology, map node, action preview or collection-transaction contract. None is required for an initial character table.
- `src/SaveToolkit.Sdk/BoundSaveDocument.cs` supplies scalar rollback and derived changes; its validators see the current state one binding at a time, not a proposed final equipment graph. `Core/Sessions/DocumentSession.cs` has per-document locking, scalar history and action dispatch; actions own their atomicity. A non-undoable action clears history. Whole-game validation belongs in the plugin, using a staged final-state model before patching.
- `Core/Export/WorkspaceExporter.cs` verifies dirty primary documents by reopening an overlay, preserves other files and mirrors byte-identical backup twins. Multiple outputs already work, but two dirty documents rewriting the same sibling are rejected. This does not itself prove cross-file gameplay consistency or re-open every rewritten sibling as an independent document.
- `web/src/components/document/TableView.tsx` virtualizes and filters the rows in one loaded table, not all unexpanded pages. Its cells render only fields/text; an `ImageNode` cell is currently blank. Table fields omit visible confidence/description, showing warnings mainly as a title tooltip. `fields/FieldControl.tsx` renders enum options as a native select; `ActionButton.tsx` provides a parameter dialog and static confirmation. There is no icon picker, linked materia grid, global lazy-data search, map or semantic diff/review screen.
- Fresh sample measurements reused scratch `verify.py`/`check-ids.py` and added independently written `verify_relationships.py`, all run with `python -I`, reading ZIP entries directly. There are **55 payload entries**: 40 Remake including backup twins, 12 retail Rebirth and 3 demo; primary gameplay counts are 19/11/2, not 55 independent experiments. All gameplay chains end at EOF; no `GVAS` occurs in these payloads. Scratch reports are `measurements.json` and `relationships.json`; no downloaded implementation was executed.
- Fresh character evidence: Remake primary `ff7remake000` at absolute `0x30/0x40/0x44/0x50` gives level 38, HP/max HP 5,713/5,713 and XP 135,772. Retail Rebirth uses a candidate `0x100` character stride: first seven records in `ff7rebirth000` contain level 41, with Cloud candidate HP 4,231 and XP 148,409; slot 001 has level 15/XP 7,200 for the first five. The source supplies character names/order; numeric plausibility is verified, named in-game identity and mutability still need screenshots/differentials. Remake's character stride is `0x40`, not Rebirth's.
- Fresh relational evidence: Rebirth Cloud candidate weapon reference `300001` at `0xCC` resolves to type `1001` in both the inventory weapon family (`0x5FA6C/0x5FA70`) and weapon details (`0xB3A68/0xB3A6C`, stride `0x60`). All first-seven weapon references resolve in every supplied primary retail/demo gameplay file. Materia instance `600000` at `0xBFA68` has type `10020` at `0xBFA6C`, matching the inventory-family instance/type/quantity at `0x60A6C/0x60A70/0x60A74` = `600000/10020/1`. These are different ID domains; names attach to type IDs, equipment to instances.
- Fresh data caveats: first Rebirth retail inventory has 241 occupied entries, including 51 category-`0xD` Queen's Blood entries; demo has none. Empty inventory type IDs are predominantly `0xFFFFFFFF`, while Remake materia empties are zero and Rebirth materia empties `0xFFFFFFFF`; `id == 0` is not a sufficient universal empty-row rule. Ordinary AP tables fit supplied values, but a naive threshold calculation disagrees on Titan in three retail files: type `14011`/`0x36BB`, AP 0, stored level 1, while upstream lists four zero thresholds. Preserve this valid-looking state; summon tier needs separate evidence.

### Integrity / crypto

- **Verified plaintext and structural integrity:** fresh direct-byte reads confirm visible container headers, arrays and values; no decryption/decompression is needed for these supported fields. Our demo comparison again found **800 changed body bytes and zero changed envelope/content-header/tail bytes**. It is an uncontrolled pair, so it does not identify which gameplay action caused each change.
- `plugins/FinalFantasy7/research/integrity_search.py` and README document prior CRC/Adler/FNV/xxHash/Murmur/sum/digest searches and zero candidate matches for the three common payloads. This is scoped negative evidence, not a mathematical proof that all chunks and patches lack checksums. It was inspected, not rerun as a new exhaustive search here. GTC and PS4 code sources above patch fields without an observed FF7 hash-fix step.
- **The missing integrity work is chiefly semantic:** XP↔level, AP↔stars with summon exceptions, equipment instance ownership, inventory/detail joins, capacity/slot availability, and progress flags/counters/rewards. GTC's dependent writes demonstrate why successful structural reopen alone is insufficient. The current AP-only edit may leave stored level stale after a threshold crossing; whether the game repairs it is unknown and must be tested.
- No additional secret key is established as necessary for the supplied decrypted FF7 files. Sony outer-container handling stays with the owner's save-manager workflow. Asset-archive keys/codecs for extracting optional reference packs are a separate concern; do not introduce them into gameplay serialization or log account credentials. New variants that need integrity the plugin cannot repair remain read-only/rejected.

## Vision

- **Overview:** game/variant/build support, slot/chapter/location, party, gil and currencies, playtime, confidence and a readable list of pending gameplay changes. Distinguish active RESD from prior-state/checkpoint records and never edit both by assumption.
- **Characters:** named sheets for Remake's party/INTERmission and Rebirth's main seven, then separately researched guest/past records. Show level/XP, current/max HP/MP, base versus cached/derived stats, weapon abilities/proficiency, SP/folios and relationships where confirmed. Recalculated values are labeled read-only; unsafe/unobserved characters stay inspection-only.
- **Inventory and equipment:** search all owned stacks by name/category, show icon/description when supplied, quantity/cap, type ID, instance identity, ownership and acquisition state. Filter consumables/materials/key items/cards/gear; unknowns remain inspectable. Equipment pickers offer only compatible owned instances and reject duplicate assignment or removal of equipped objects.
- **Materia:** named colored categories, stars and AP-to-next-star, equipped owner and linked weapon/armor socket layout; distinguish duplicates by instance and AP. Allow existing-materia AP adjustments, compatible swaps, unequip and named loadout presets, with summon-specific rules. Rebirth and Remake do not share an equipment serializer.
- **Progress and collection:** chapter-clear versus current quest state, enemy intel, outfits and minigame records; Rebirth adds Queen's Blood owned/quantity/missing, decks once mapped, Treasure Trove, World Intel/Protorelic and region/Chocobo-stop checklists. An optional licensed/local map supports “show missing here”; a textual regional checklist remains fully usable without images.
- **Operations:** previewed “restock existing ordinary consumables to a chosen validated amount”, “set selected owned materia to a validated star”, “restore a compatible owned loadout” and targeted completion recipes only after proof. Exclude key items, unique rewards, summons and unknown rows from generic max-all. Add/remove means allocating/releasing proven fixed-array slots, not resizing the linked container. Every supported command is atomic and reversible, and reports skipped objects and reasons.

## Phased plan

**Phase 1 — establish semantic safety for the features already shipped. Size M; highest value/risk reduction.**

- [ ] Create a per-variant evidence ledger: absolute and record-relative offsets, width/signedness, source revision, identity domain, empty sentinel, capacity, dependencies, confidence and required patch/build gates.
- [ ] Extend embedded MIT data with categories, AP/XP tables and provenance. Investigate ordinary stack limits per category; label 99 as an upstream editor policy until observed in-game, and remove the current implication that 9,999 is safe for every item.
- [ ] Gate quantity/AP editing to supported occupied rows; exclude unknown/sentinel/unique/key/card/gear categories from generic quantity actions. Distinguish category rules from representable integer range.
- [ ] Implement staged dependency validation for AP/stars, preserve summon tiers, and reject conflicting aliases that address the same bytes (e.g. gil overview versus inventory). Keep normalizing untouched original values out of serialization.
- [ ] Add single-field golden-byte and threshold-boundary cases, including below/at/above a materia threshold, unknown IDs and sentinel rows; perform a console load/resave comparison on one existing edit per writable game.

## Acceptance criteria

- [ ] Changes stay inside `plugins/FinalFantasy7/` during plugin implementation; any SDK/Core/UI feature is handled as a separately owned framework change. No private saves/assets committed and no runtime plugin filesystem/network calls.
- [ ] Every exposed field/operation has a variant/build-specific source and byte-evidence entry, with numeric IDs, instance references and display identifiers distinguished. Candidate meaning is Inferred; raw unknowns remain Unknown; game compatibility is reported separately.
- [ ] All supplied supported payloads retain byte-identical no-op output, including empty allocations, unknown words, previous-state records, common files, padding and tails. Untouched out-of-policy values are not normalized.
- [ ] A one-field edit changes only approved bytes plus explicitly justified dependencies. Conflicting aliases, unsupported rows, invalid references and capacity violations reject atomically with no partial changes.
- [ ] Ordinary materia AP/star crossing works below/at/above each validated threshold; summon level is not derived from repeated-zero AP arrays. Unknown or untested materia cannot be bulk-maxed.
- [ ] Character sheets reproduce owner-observed HP/MP/XP/level and equipment for Remake main, INTERmission and retail Rebirth; derived/cached stats are distinguished. Demo and guest/past records retain separate gates.
- [ ] Equipment and loadouts resolve actual owned instances; duplicates, incompatible slots, dangling references and removal of equipped objects are rejected. Inventory/detail and owner relationships remain consistent after serialization and reload.
- [ ] Named inventory/materia/card search reaches every supported occupied row without manually opening pages; initial views remain bounded and no unbounded raw/object tree is added. Retain the existing initial-view node/per-sample open-time budgets unless explicitly rebaselined with measurements.
- [ ] The 145-card reference crosswalk is reviewed for duplicate/wrong display numbers and missing mappings; acquisition, ownership quantity, deck composition and opponent wins are separate controls. Unknown card IDs survive unchanged.
- [ ] Bulk commands show target count, skipped objects/reasons and dependent changes; cancellation changes nothing. Apply, undo and redo preserve exact bytes, including unexpanded rows and legal original values outside new editing policy.
- [ ] Existing plugin conformance plus meaningful dependency/reference/boundary/malformed-input tests pass during implementation. Sample-dependent tests skip when absent; this plan does not claim a new test run.
- [ ] Descriptions/icons are optional, local/offline after import and attributable to a cleared source/user pack; no GPL/NC/proprietary implementation or art is silently relabeled MIT. Missing packs leave usable names/categories/raw IDs.
- [ ] Progress/map writes remain disabled until known-state diffs and human tests demonstrate complete flag/counter/reward/actor effects. Repeated placeholder addresses are not exposed as independently verified objectives.
- [ ] Each newly enabled gameplay operation is loaded, observed, used and resaved on its supported PS5 variant; a second import confirms the intended state. Only a human promotes maturity to Stable, with the scope of validated operations documented.
- [ ] README updates include supported revisions/regions, source SHAs/licenses, verified versus inferred fields, tested limits, known failure modes, SDK requests and the remaining demo/guest/progress restrictions.

## Open questions & risks

- Can the owner produce genuinely controlled pairs and perform PS5 import/load/resave tests for all three titles? Existing distinct slots and byte-identical backup twins cannot answer cause-and-effect questions.
- Does the game recompute stored materia stars from AP, cached character stats from XP/gear, and ownership fields on load? Until tested, preserve coherent known state and avoid both incomplete writes and aggressive repair of pre-existing anomalies.
- What are the actual caps and uniqueness rules for each item/card/material/token family? GTC's 99 and this plugin's 9,999 are tool policies, not universal game contracts. Rebirth summons and story guests have special behavior.
- What state distinguishes Remake main/INTERmission, Rebirth live/past/guest characters, current versus previous RESD, and the MLSD/NVSD families? Equal record lengths and plausible numbers do not establish editable semantics.
- Can a complete local reference pack be generated without bundling the NC DataObject dependency, and who clears game-text/icon distribution for a multi-game toolkit? A data importer cannot itself supply missing rights or guarantee an asset-to-save ID join.
- Do latest patches or regions change sizes, offsets, serial rules or integrity? Current exact-length/version gates should remain; do not silently accept newer files because the filename matches.
- Story and world edits can cause softlocks, stale rewards or inconsistent actors while passing every structural test. Gilgamesh reset, guest party composition, teleport and generic 100% presets remain research-only until their own prerequisites and reversals are demonstrated.
- Item creation is a coordinated fixed-slot transaction, not a name-picker convenience. New items may need inventory, weapon/materia details, ownership, acquisition flags and counters together; do not conflate it with changing an existing quantity.
- Reference metadata and visible confidence can become stale after structure changes; UI caches, Core view indexing and undo must be exercised together before dynamic loadouts or removals ship.
