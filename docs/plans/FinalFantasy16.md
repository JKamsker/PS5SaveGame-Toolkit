# FinalFantasy16 — improvement plan

## Summary

The `ffxvi` plugin already preserves and edits existing main-inventory stacks, including gil, AP and renown, and repairs the PS5 Faith CRC; it is Experimental and has no documented console validation. A substantial improvement is achievable without replacing that foundation: named inventories, useful equipment and ability sheets, contextual limits, and eventually validated progression and collection controls. Independent research in this round matched all 172 distinct main-inventory IDs observed in the supplied saves to named published entries, but that does not establish complete game coverage or permission to redistribute the dataset. The three leading blockers are a licensed, versioned reference-data source; controlled saves proving active banks, limits and dependent gameplay state; and human PS5 load/save/reload validation. Rich pickers, transaction previews and reversible structural editing need framework/UI work, while useful read-only views and fixed-width actions can use today's contracts.

Read the prescribed project documentation and [issue #1](https://github.com/JKamsker/PS5SaveGame-Toolkit/issues/1). This round changed no repository files and ran no builds/tests/package managers; test statements below describe source assertions, not a fresh test run.
- `plugins/FinalFantasy16/SaveToolkit.Plugins.FinalFantasy16/FinalFantasy16Plugin.cs`: supports only outer title IDs PPSA10665 retail and PPSA13803 demo, expected gameplay/system basenames and matching container versions. **PPSA01288 is Sackboy**, mentioned here only in the explicit foreign-title rejection test (`FaithFormatTests.cs`); `docs/formats/PPSA10665.md` records stale/generated SFO values as the reason for historical confusion. Do not add it as an FF16 title.
- `FaithContainer.cs`: validates 16-byte plaintext header, CRC at `0x04` over `0x10..EOF`, block sizes/bounds/alignment and zero terminator; preserves duplicate types, unknown blocks and trailing bytes. On-disk advance is declared size minus 8, payload length declared size minus 24. No PC PNG/XOR/compression layer belongs in PS5 output.
- `FaithSchema.cs`: per-block version/length gates, including PlayerData `202211161` / 272 or 1,536 bytes, ItemData `2021110401` / 36,448 bytes and UserData `2021061001` / 104 bytes. Demo does not inherit the extended retail player schema.
- `FaithInventory.cs`: main capacity 1,200, secondary capacity 100, 16-byte records. Enables only substantiated dense main allocators; IDs, keys, indices, flags, padding and other banks are preserved. No add/remove/reorder, equipment selection or secondary-bank edit exists.
- `FaithDocument.cs`: Overview/Inventory/Structure/Hex tabs, non-negative i32 stack editing, read-only level/XP, child level/XP and time. Maximum `int.MaxValue` is a storage bound, **not a proven gameplay cap**. Known resources appear on Overview; there are no bulk actions or preset implementations. `CanEdit` depends on a supported inventory with an editable stack.
- `FaithItemNames.cs` and `Resources/ResourceItems.tsv`: only three embedded names, IDs 1 Gil, 2 Renown, 3 Ability Points. All other current rows have numeric labels. `FaithExplorer.cs` limits lazy expansion to 64 children and leaf tables to 128 words; raw words have unknown semantics.
- `SaveToolkit.Plugins.FinalFantasy16.Tests/FaithSampleTests.cs`: assertions cover every ZIP record, known values, dense stack patches, unrelated-byte preservation, atomicity/isolation and CRC reversal. `FaithFormatTests.cs` covers CRC vectors, valid-CRC structural corruption, unknown/duplicate blocks, allocator bounds and demo gating; `FaithExplorerTests.cs` covers bounded traversal and blob ranges. `FinalFantasy16ConformanceTests.cs` raises the sample limit to 80; `FaithSamples.cs` skips absent archives. These cannot prove game acceptance.
- **Fresh independent byte verification:** reused scratch clones and reviewed `inspect.py`; wrote and ran only our own read-only Python scripts with `python -I`. `verify_extended.py` reads ZIP entries directly, checks framing/CRC/allocator keys, and makes in-memory gil+1 patches without writing samples. Results are in scratch `verification.json`; all research tools/downloads stayed under the assigned scratch directory.
- Retail: **60 records, 51 distinct whole-file contents, 59 gameplay / 1 system, 49 populated / 10 empty gameplay**. Demo: **12 records, 12 distinct contents, 11 gameplay / 1 system**. All 72 CRCs and terminator walks match; all 60 populated gameplay records pass independent fixed-width gil-patch CRC and unchanged-byte checks. Duplicate paths/content are not independent experiments, and hashes do not establish independent playthroughs.
- First retail autosave: level 42, XP 13,891, gil 104,594, AP 5,942, 172 allocated main rows. All **172 distinct observed main IDs** match named entries in the reused item/equipment CSVs; the demo main bank contains only resource IDs 1 and 3. Published CSV totals are 373 general rows / 353 named and 537 equipment rows / 526 named, counting `(no name)` entries separately.
- New read-only leads occur in all **70 gameplay records**: PartyData type 2 `2021112401` / 168 bytes; QuestData type 3 `2022052701` / 11,592; EquipmentData type 13 `20220104` / 72; SkillData type 27 `20210422` / 96. The dimensions match the upstream template; semantic correctness remains **Inferred** without controlled game observations.
- Equipment's first retail six words join to Defender, Circle of Heaven, Sun Bracelets and three accessories. Across all three six-word banks there are 29 nonzero retail values / 10 demo values; one value, **900000**, has no published equipment-name match in either title. Preserve it as unknown; do not invent a sentinel meaning or reject an existing save because of it.
- Template-designated skill-level bytes contain 0–3 in retail and 0–1 in demo. This is an observed distribution, **not permission to write every skill to 3**. PartyData's candidate map ID joins to 602000/The Hideaway in the first retail autosave and 392000/Phoenix Gate in the first demo autosave; gamemap IDs can have multiple asset-path rows.
- Secondary initialized counts are 14 in populated retail and mostly 14 in demo (one 11). Its entries include separate gil, boyhood-looking gear, potions and tonics, plus an ID-zero record. This supports researching a stage/bank relationship, **not** treating it as a second editable current inventory. Secondary quantities can differ from the main bank.
- SDK/Core already provide lazy sections, tables, enum/flags specs, descriptions/warnings, assets/blobs, atomic scalar batches, parameterized actions, stable value IDs, value undo/redo, multi-file `Serialize()` and export re-open checks (`src/SaveToolkit.Sdk/**`, `Core/Sessions/DocumentSession.cs`, `Core/Export/WorkspaceExporter.cs`). Do not request those facilities as if missing. `BoundSaveDocument` has per-field validators, not a reusable complete-candidate-state validator; plugin overrides can handle dependencies today.
- Concrete gaps: `Views/ViewNode.cs` has no catalog-reference, equipment-slot, skill-tree or map node; `EnumOption` has no icon or catalog metadata. `web/src/components/document/TableView.tsx` renders only field/text cells despite the SDK allowing other nodes; it has search/virtualization, no selection or category facets, and table cells omit confidence/description presentation. `FieldControl.tsx` uses native enum selects. `DocumentSession` stores scalar changes and clears history for non-undoable actions. `IGamePlugin.Open(ISaveFile)` has no injected reference-data context; plugins cannot fetch assets/tables or read user directories themselves.

### Integrity / crypto

- The [pinned FaithSaveFile checksum implementation](https://github.com/Nenkai/FF16Tools/blob/b87c2f22a8ea630cb03f7b2198af84c7709a1b0c/FF16Tools.Files/Save/FaithSaveFile.cs) repairs CRC-32/ISO-HDLC on binary inner files. Independently confirmed LE stored word at `0x04` equals Python `zlib.crc32(bytes[0x10:])` for all 72 supplied records. Polynomial/reflection behavior is already implemented/tested in `FaithContainer.cs`; no additional key is needed for these decrypted PS5 inner files.
- PC PNG chunk CRC, XOR and preset-dictionary compression belong to a separate outer platform adapter. The [author's save research](https://nenkai.github.io/ffxvi-modding/resources/other/save_files/) and reviewed MIT code establish the PC path, not PS5 PNG output or Xbox/WGS conversion. No keys from a user account were read or required; no cryptographic credentials are requested by this plan.
- No additional signature/MAC/per-block checksum has been substantiated. CRC plus parser reopening cannot establish semantic validity: equipment ownership, AP costs, quest dependencies and any system/slot metadata may matter. Investigate failures with controlled edits rather than inventing a missing hash. Preserve original filenames/slot roles, schema variants and opaque bytes; encrypted console backup handling remains outside this plugin.

## Vision

- **Overview / Character:** save role, schema, location and play time; Clive adult/child state explicitly separated; level/XP and derived stats only as supported by game data. Gil/AP/renown show known constraints and provenance. Unsupported layouts explain which curated section is unavailable.
- **Inventory:** named consumables, materials, weapons, belts, vambraces, accessories, key items/curiosities; searchable categorized rows with optional icons, description drawer, current quantity/cap and DLC/NG+ availability. Unknown IDs remain visible. Distinguish allocated zero stacks, owned items and active bank instead of equating them.
- **Equipment / Abilities:** current six equipment slots plus separate historical/virtual banks, owned legal choices, projected stat changes; Eikon loadout, unlock/learn/master state and cost/refund preview. Torgal/other party values stay read-only until separately mapped. Presets apply only supported, owned/unlocked combinations.
- **Progress / Collections:** read-only quest/sequence audit, hunts, letters, orchestrion, lore, curiosities, recipes, obelisks and treasures with per-list coverage. Optional map pins need asset rights and a verified transform. No generic 'complete every quest' action or arbitrary teleport.
- **Useful bounded actions:** refill selected existing consumables to the actual current cap, set a chosen amount for selected supported materials, adjust resource balances within proven limits, restore a known previously allocated sold item if supported. Show an exact preview, skip unsupported rows with reasons and undo the whole action once.
- **Change review / Advanced:** human-readable before/after changes with affected banks/derived fields, byte-preservation summary, experiment status and undo; retain lazy structural/hex views for unknowns. Preserve every existing unknown value, including 900000 and game text markup, without manufacturing meaning.

## Phased plan

Sizes are relative implementation effort after the stated evidence arrives: S roughly 1–3 engineering days, M about a week, L several weeks; console access/research wait time is additional. Each feature gets independent schema and evidence gates. Framework changes are requests to the owning agents, not permission for this plugin implementation to edit `src/` or `web/`.

**Phase 1 — useful named inventory and reproducible evidence (M; highest immediate value).**

- [ ] Preserve the current parser/writer and add a machine-readable manifest of title, outer role, block type/version/length, supported fields, provenance and evidence status.
- [ ] Secure the name-table rights route; add deterministic offline conversion to a minimal immutable catalog with numeric ID, localized plain-text name, source/version and coverage. Keep unknown IDs and raw markup available; tokenize supported game formatting into safe text rather than rendering it as HTML.
- [ ] Name all currently observed supported main rows; separate resource balances from ordinary item categories only where sourced. Add a read-only secondary-bank diagnostic with a conspicuous unconfirmed-role label, not ordinary editable inventory.
- [ ] Add focused tests for name lookup, missing/duplicate IDs, 900000, markup, zero stacks, fallback locale and unsupported schemas; update README source/license/coverage statements.

Evidence: R1/R8; current 72-record corpus is enough for byte-level regression and observed-ID coverage, not active-bank semantics. Acceptance: every observed main ID resolves or has an explicit fallback; unsupported files remain accessible/preserved. Risk: low for labels, medium for redistribution rights and category assumptions. Works with current text/table nodes; icons do not block it.

**Phase 2 — read-only gear, abilities, location and growth context (L).**

- [ ] Add composed readers for PartyData, EquipmentData and SkillData, gated by the measured block triples; separate all three equipment banks and all skill/new/protect arrays. Decode the common player prefix separately from the extended palette suffix.
- [ ] Join equipment IDs, map IDs, command/skill/summon data and growth tables from matched local reference data. Keep raw IDs beside names and preserve any many-to-one map/asset relationships.
- [ ] Use matched PC binary/XML captures to identify fields and controlled PS5 captures to prove the active bank, equipment slot ordering, byte-index-to-skill-ID mapping, Eikon flags and AP accounting. Establish whether XP is within-level or cumulative and how HP changes on level-up; do not assume a setter for one is enough.
- [ ] Build read-only equipment/ability views and a coverage report for retail/demo/DLC. Show 900000 and unseen modes without substituting an item name. Read cached game metadata only; do not install a runtime hook in the server/plugin.

Evidence: R1/R2/R4/R9/R17/R18. Acceptance: human-observed equipped items and learned ranks match the decoded views on each supported state; ambiguous fields stay Inferred/Unknown. Risk: medium for reading, high if UI conflates historical and active banks. Current sections/tables suffice initially; R5/R6/R16 improve the experience.

**Phase 3 — context-aware existing-stack edits and bounded bulk actions (M).**

- [ ] Resolve `ItemCap` versus `UseItem` capacity, upgrade ownership, difficulty/NG+/DLC effects, unique/key items, and separate gil/AP/renown constraints. Unknown cap means no 'max' preset; do not truncate existing over-cap values on open.
- [ ] Replace generic storage bounds with proven bounds for supported fields; preserve legacy experimental behavior only through an explicit documented policy, with no claim it is legal. Keep provenance and exact affected bank visible.

## Open questions & risks

- **What is active when?** Main and secondary banks contain different resources; demo gameplay may use the secondary bank or a distinct stage context. Equipment's three banks and 900000 need direct observations before pickers or consumable editing can claim the current state. Do not overwrite both banks to force agreement.
- **How are growth and abilities persisted?** XP basis, level-up effects, HP recomputation, new/protect flags, palette changes, DLC Eikon state, skill-index mapping and refund rules remain unconfirmed. A runtime ability effect does not prove its save representation or a permanent legal state.
- **Where do caps come from?** UseItem overrides ItemCap and has upgrade variants; mode/DLC/hardcoded exceptions may remain outside the tables. Editing renown may require separate reward state, and arbitrary high gil/AP values might clamp on load. Trainer constants and observed maxima are not limits.
- **How representative is the corpus?** Retail has 51 distinct contents, not 60 independent experiments, and some records are empty/legacy. No controlled full-game DLC/mode matrix, PC XML, Xbox/WGS or additional-region saves are available. Do not label a block's presence as proof DLC is owned or fully mapped.
- **Which schema dimensions are stable?** Same PlayerData version occurs with different lengths; observed AbyssGate/type-63 versions have different lengths, and small system WorldMapConfig differs from the template's larger gameplay case. Gate each block independently and preserve unmapped suffixes/variants.
- **Can reference data be distributed?** Nenkai's tool/layout code is MIT, documentation CSV permission was not established, wiki prose has share-alike terms, authored guide data is restricted and images remain separately protected. Local extraction reduces redistribution needs but still requires an owner-approved usage route; fetching at runtime is not an automatic rights workaround.
- **Are there external dependencies beyond CRC?** None is presently substantiated. Investigate with exact before/after trials and preserved system data rather than assuming a signature. If a dependency is found, use existing multi-file contracts first and request only the missing coordination.
- **Can sold-item recovery avoid structural editing?** Allocated zero stacks may retain enough state; verify before implementing free-list mutation. Quest keys, consumed unique materials, recipe access and equipped/shortcut references could defeat naive item restoration.
- **Source quality/search limits:** paid-service claims, forum anecdotes and cheat dumps are leads only; public searches did not establish a complete alternative PS5 editor. No untrusted downloaded implementation was run. Future implementation must review tools/dependencies and retain platform and license boundaries even when a demonstration appears to work.
