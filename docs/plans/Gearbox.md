# Gearbox — improvement plan

## Summary

Gearbox already preserves and edits decrypted PS5 Borderlands 3 (PPSA01463) and Tiny Tina's Wonderlands (PPSA01493) GVAS/protobuf files, but inventory is mostly indices and byte counts. The best next investment is a named inventory and equipment browser, followed by conservative edits to existing item serials, named SDUs, character builds, Guardian/Myth progression and carefully scoped mission repair. This research independently validated item checksums and basic serial decoding for all 93 BL3 and 68 Wonderlands primary-file serial occurrences; the existing databases already name 83 and 51 respectively. The three largest blockers are incomplete/versioned reference data and artwork rights, missing controlled PS5 saves and in-game validation of dependent edits, and BL4's unestablished PS5 inner codec/file roles. Structural undo and coordinated character/profile ownership are additional framework prerequisites for a trustworthy item-management experience; they do not block the initial read-only browser. BL4 must remain a separate, gated feasibility track rather than delaying useful BL3/Wonderlands work.

### Integrity / crypto

- **BL3/TTWL container:** existing public PS4 role masks decode all supplied records; own probe re-encodes the 12 primary payloads identically. The [pinned zlib BL3 source](https://github.com/apocalyptech/bl3-cli-saveedit/blob/d459b28a7e88f1a5ae0f16118272d8a5383b8b04/bl3save/bl3save.py) and plugin describe feedback XOR, not authenticated encryption/compression. No extra wrapper checksum is established; successful protobuf parsing cannot detect all corruption. Preserve title/role/header/tail checks and unknown wire bytes. No missing secret key blocks these two games.
- **Independent item integrity:** pinned `datalib.py` sources above describe version byte + signed big-endian seed, seed-driven rotation/XOR, then a big-endian 16-bit fold of CRC32 over `header + FF FF + plaintext bits`. Own code verified all 161 serial occurrences and exact original-seed round trips. Version 4 BL3 reroll bytes and version 5 Wonderlands Chaos data require separate layouts. Keep unknown customizations/tails intact; valid CRC does not mean a valid balance/part combination. Do not re-seed or upgrade all serials on no-op; normalized seed-zero codes are an explicit exchange representation only.
- **BL4 PC framing:** [iyre encryption notes, c9be7ba](https://github.com/iyre/bl4-save-tools/blob/c9be7baec6f1df0c348eaaebbed331d635a1f7a9/docs/encryption.md) describe AES-256-ECB with Steam/EGS-account-derived key, PKCS7, zlib YAML and appended little-endian Adler32/uncompressed length; MIT. Existing scratch notes hash-match that revision. A candidate PS5 codec must independently pass padding, bounded decompression, stream/trailer Adler32, length, schema and inverse-round-trip checks. PS5 derivation, role/framing, compression and any additional integrity remain unknown. No private account identifiers/keys were read, requested or brute-forced. A PC static key or 16-byte alignment alone is insufficient evidence.
- **BL4 preservation risk beyond crypto:** YAML emission can change ordering, quoting, tags, scalar types or opaque fields; a permissive parser is not proof of lossless writing. The inspected MIT `serial.rs` token-preservation design is a useful lead, but PS5 plaintext is absent. Retain original encrypted bytes on no-op; require lossless scalar/token patching plus bounded validation before enabling BL4 writes. This work should not alter the proven BL3/TTWL protobuf path.

## Vision

- **Character / Build:** named class and dual-class branches, exact XP/level, real named skills and allocations, Hero stats where verified, equipment-dependent versus saved stats distinguished, legal point budgets, respec/restore presets. Derived combat values remain unavailable or labeled estimates until game-data formulas and hotfix context are reproduced.
- **Backpack / Equipment / Bank / Lost loot:** searchable named item list with optional licensed icons, rarity/type/manufacturer/element, level, Mayhem or Chaos item tier, favorite/junk and equipment location. Select an item for a card showing base name versus generated name, description source, serial code, balance/part paths and confidence. Inventory and profile containers remain visibly distinct.
- **Safe item workbench:** edit existing level/reroll/known tier first; then constrained part/anointment/enchantment selection, duplicate/import from `BL3(...)` codes within the explicit game context, create from known legal templates, equip/move/delete with capacity and slot checks. Identical serials can represent distinct inventory rows. Support a previewed selected-item bulk operation such as “match character level”; unknown items are preserved and excluded with a reason.
- **Progression:** named SDUs with purchased tier/capacity; fill ammo to verified current capacity; Guardian/Myth sheets with allocations, spent/unspent totals and perk gates; distinct BL3 Mayhem 0–11 policy versus item Mayhem 0–10, and build-specific Wonderlands unlocked/active Chaos versus item rarity tier. These proposed ranges require current-build verification before write enablement.
- **World / Missions / Collectibles:** per-playthrough missions, objective/reward/branch context, named travel stations, map-grouped challenges/crew collectibles or Wonderlands dice/shrines/scrolls. Start with checklists; offer a map only when coordinate transforms and art rights exist. Curated side-mission repair and unlock presets show prerequisite and reward consequences; no undifferentiated “complete everything” button.
- **Review / Raw:** readable before/after item and progression changes, affected files and capacities, a single-step undo for each operation, raw IDs for unmapped content, reference-data provenance/build coverage and clear unsupported reasons. A BL4 tab appears only after an independently established decoder can classify the supplied file.

## Phased plan

### Phase 1 — Named read-only inventory and semantic catalogue (M)

- Goal: immediately turn opaque byte counts into a useful browser without changing serials.
- [ ] Introduce composed serial reader/database resolver/item-reference services inside `plugins/Gearbox/`; retain separate game resources and unknown fallbacks. Keep files ideally <300 LOC and below the workspace 500-line hard limit; no artificial partial splits or repository tooling changes.
- [ ] Port/adapt only the audited zlib serial algorithm; preserve raw seed, database version, trailing bits and each original byte sequence. Add CRC/bounds/version diagnostics per item rather than preventing unrelated currency editing for an undecodable serial.
- [ ] Embed the minimal approved versioned name/index/part-key data with provenance; distinguish family labels from full in-game names. Map cosmetic pickup families explicitly instead of guessing names.
- [ ] Add read-only selected-item detail, named slot/SDU/resource labels, serial code display, named skill/rank/mission/challenge summaries where a mapping is proven; keep large lists lazy/bounded.
- Evidence: current 161 occurrences, the pinned resources and missing-cosmetic path list; additional data required for full names/localization/icons. Risk: stale index widths and names falsely presented as exact. Gate: corpus coverage counts reproducible and all original files remain identical. Requirements: R1, R6, R7, R8, R12.

### Phase 2 — Conservative existing-record edits (M)

- Goal: item-level utility plus safe storage/progression controls before any insertion/removal.
- [ ] Enable level changes with exact bit-position patching and CRC repair while preserving unknown remainder/seed. Add original-value restoration and selected supported-item bulk leveling; validate proposed scope before mutation.
- [ ] Decode/display reroll count, item Mayhem/Chaos and generic parts; enable only individually verified writes, retaining game/item distinctions. Validate flags before offering favorite/junk toggles.
- [ ] Name existing SDU tiers/capacities; allow known existing SDU tiers and ammo refill only after build-specific cap/dependency checks. Read endgame/skill allocations before editing them.
- [ ] Address existing leveling-budget limitations through explicit restore/respec policy and derived-state tests; do not multiply skill points through repeated level operations.
- [ ] Perform isolated restore/load/check/re-save tests for each enabled edit family and compare game-rewritten state.
- Evidence: one-variable before/after saves, screenshots/transcribed item cards and matching profile/character pairs. Risk: game clamps/removes gear or progression recomputes; no-op codec success alone is insufficient. Gate: target edit survives PS5 load/re-save without unrelated changes. Requirements: R2, R6, R10, R12, R13, R16.

### Phase 3 — Reversible inventory management and item construction (L)

- Goal: constrained part edits, import/duplicate/equip and coordinated bank transfers.
- [ ] Establish legal balance/part pools, required/excluded parts, DLC context and special-item restrictions; provide a compatible part picker. Item creation first uses known legitimate serial templates, then validated balance/part generation.
- [ ] Implement stable document-local row identities independent of list position or serial hash, including duplicates; rewrite every affected equipment index/pickup-order/capacity relationship transactionally.
- [ ] Add whole-item replacement and constrained anointment/enchantment/reroll controls; reject wrong-game, malformed, checksum-invalid or unsupported-version imports. Both games can use `BL3(...)` wrappers: require explicit game/database context rather than prefix-based game detection.
- [ ] Implement insert/remove/duplicate/equip with structural undo; coordinate backpack↔bank/lost-loot moves using one explicit generation-matched profile/character operation. Preview available capacity; never silently discard overflow or special/unknown gear.

## Acceptance criteria

- [ ] Implement later only within `plugins/Gearbox/`, following `docs/PLUGIN_GUIDE.md`; record concrete framework requests in the plugin README and give SDK/Core/UI work to their owners. Add no plugin-folder hooks/build targets/tooling; retain maintainable composed classes.
- [ ] The read-only item reader reproduces 93/93 BL3 v4/db62 and 68/68 TTWL v5/db59 CRC/header/original-seed no-op results; known-name and complete-parts coverage counts match or improve the baseline with explained mappings. Count duplicate occurrences honestly.
- [ ] Full names, family names and raw asset IDs are distinguishable; missing/outdated databases never invent labels, discard serials or enable unsafe part edits. Unknown versions/customization tails remain preserved and read-only where necessary.
- [ ] Every claimed sample retains exact whole-file no-op bytes, including unknown protobuf records, headers, tails and opaque serials. Edits change only intended semantic data, required enclosing lengths and genuine integrity bytes; feedback encryption differences are assessed after decoding.
- [ ] Existing-item edits validate CRCs, bounds, supported database versions and game-specific fields; wrong-game codes, malformed Base64, truncation, invalid part indices and unsupported customizations fail atomically. Successful CRC is never presented as proof of legal gear.
- [ ] Bulk edits preview complete scope across lazy pages, report skipped unknowns, revalidate on apply, and undo as one operation. Repeated level changes cannot silently accumulate skill points through editor policy.
- [ ] Structural operations preserve duplicate identity, equipment/pickup references and verified capacities; bank transfers/rank updates affect only explicitly selected same-title/same-generation files. Dirty-session conflicts are explained before mutation; all returned files reparse.
- [ ] Undo/redo restores exact original bytes after item edits, imports/deletions/transfers and coupled progression operations, including previously unexpanded lists. Stale row IDs cannot edit a different item after a structural rebuild.
- [ ] Guardian/Myth edits conserve documented XP/token/point/perk relationships; approximation, cap and game-build limits are visible. Unsupported class changes, story resets and reward-dependent actions remain unavailable until separately verified.
- [ ] Missions/collectibles use verified ID/name/ownership crosswalks and playthrough context; a controlled one-record game change validates each enabled recipe. No achievement, entitlement or reward outcome is promised from a flag alone.
- [ ] Item/category search, detail, icons/fallbacks and bulk scope remain bounded and keyboard-accessible; query semantics explicitly cover either a page or full container. Existing ≤100-record lazy behavior remains responsive; opening supplied samples retains the existing two-second test target on its documented test environment.
- [ ] Conformance and meaningful format-specific tests pass after implementation, with sample-dependent tests skipping when fixtures are absent. New tests cover preservation, mutation boundaries, corruption and dependent behavior; research-phase README counts are not reported as freshly executed checks.
- [ ] Every packaged code/data/art source has a pinned provenance manifest and applicable notices/permissions; approved facts work fully offline. GPL/AGPL implementation is not ported without an explicit compatible licensing decision; no downloaded code is run blindly.
- [ ] A human documents successful PS5 load, intended effect and game re-save for each advertised write family before gameplay compatibility is claimed; only the owner promotes Stable. Original saves and decoded private data never enter version control.
- [ ] BL4 is added only after file roles and PS5 derivation/framing are independently proven on multiple controlled samples, all integrity/length checks pass, and exact no-op round trips succeed. Otherwise PPSA01494 remains excluded with a precise blocker report.

## Open questions & risks

- Which PS5 game patches/DLC/hotfix states produced the supplied saves? Current headers prove engine/build-family compatibility, not catalogue completeness. PC hotfix-era stats and console patch timing may differ.
- Can reference-data redistribution be approved for minimal factual index/name maps, and can optional artwork be licensed? Public availability and source-code licences do not establish rights to extracted descriptions/textures; runtime fetching also needs permission.
- Are the absent part keys exclusively non-gear/cosmetic families, and do unusual customization counts carry payloads needing a new parser? Preserve them until sampled; do not generalize from zero-customization examples.
- What is the authoritative Guardian mirror reconciliation rule on PS5, and are newer opaque profile tags involved? Can Myth XP/rank be derived exactly for the relevant build, including rotation/capped-stat constraints?
- Which SDU/skill/difficulty changes are sufficient in existing records, and which need challenges, perk flags, reward state or mission gates? The current high numeric editor limits must not become “legal max” presets.
- What is BL4's 1,888-byte file actually storing? There is no evidence yet that it contains character gameplay; console inner encryption, account binding, compression or framing may differ entirely from PC.
- For BL4 permissive references, is all serial implementation independently sourced or copied/adapted from AGPL research? Audit file history and notices before reuse; attribution alone is not a licence grant.
- Mission resets/completion can strand characters or double-grant rewards; Wonderlands collectibles may span profile and character state. Prioritize observation, known-state repair and explicit scope over global completion.
- Cross-save/platform conversion, new save-slot creation, premium/online entitlements and exact combat-stat simulation are not established by this plan. The existing exporter only rewrites imported file paths; slot creation would need a separate host contract and evidence.
- Estimated sizes assume reference data and console access become available. BL4 and unrestricted item generation remain research-dependent; do not make them critical-path commitments for the first named-inventory release.
