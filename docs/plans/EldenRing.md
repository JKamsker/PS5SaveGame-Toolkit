## Summary

The plugin already understands the sampled decrypted PS5 `memory.dat` allocation, validates character/profile mirrors, and permits a tightly bounded four-byte held-rune edit; it is Experimental, with no console reload evidence. A substantial upgrade should deliver a named character sheet, searchable inventory and storage, an equipment/loadout view, and evidence-backed progress checklists before expanding into item creation and world-state changes. Independent scratch probes during this planning round reproduced the existing character mapping, located plausible inventory/storage/event structures, and successfully decoded the embedded regulation payload into a BND4-signature parameter archive. The top three blockers are **independent differential PS5 saves and human reload validation**, **version-matched semantic/dependency evidence for inventory, stats and flags**, and **an approved licensing/distribution route for names, descriptions, icons and community data**. Basic read-only expansion and selected fixed-size edits can use today's SDK; imported reference packs, rich inventory controls and reversible structural editing require specific framework/UI work below.

This round made no repository changes and ran no repository builds/tests; historical pass counts below are README claims, not new test results.
- `plugins/EldenRing/SaveToolkit.Plugins.EldenRing/EldenRingPlugin.cs`: `eldenring` v0.1.0; retail JP PPSA03169, Asia PPSA04608, EU PPSA04609 and US PPSA04610 are registered. Probe checks the title, `sce_sdmemory/memory.dat` role, size, magic and sentinel. Only JP has sample coverage; the other regions are inferred, and Network Test titles are excluded.
- `.../EldenRingLayout.cs`, `.../EldenRingParser.cs`: ten `0x280000` slots after a `0x70` PS header; user data 10 at `0x1900070`, length `0x60000`; regulation allocation at `0x1960070`, length `0x240010`; minimum size `0x1BA0080`. The variable GaItem walk locates PlayerGameData rather than scanning for a name or using a universal fixed offset. Legacy <=81 uses 5,118 item-map entries; newer layouts use 5,120. Legacy support has synthetic evidence only.
- `.../CharacterSlot.cs`: writes require profile version 90 and all active character versions 150. Other structurally accepted versions are read-only. Active bytes determine presence; inactive residue is preserved. `EldenRingParser.ValidateCharacter` rejects invalid names, profile disagreements, attributes outside 1–99, level inconsistent with `sum(attributes)-79`, implausible rune state and time/history disagreements. These are the supported plugin invariants, not proof that every game-accepted save must satisfy them.
- `.../EldenRingDocument.cs`: Profiles/Characters/Raw tabs; name, level, elapsed time, lifetime runes and all eight attributes are read-only. Held runes alone are writable, capped at `min(existing lifetime total, 999999999)`. Serialize reparses patched bytes and returns a copy. No inventory, equipment, class, blessing, quest or flag model exists yet; no name-writing or derived-stat transactions exist.
- `.../EldenRingHexExplorer.cs`: lazy raw sections, copied bounded blobs and a 64 KiB page limit. Preserve this inspection path and all unknown bytes when adding curated views.
- `plugins/EldenRing/SaveToolkit.Plugins.EldenRing.Tests/{SampleTests,EditingTests,CorruptionTests,LayoutTests,HexExplorerTests,EldenRingConformanceTests,SyntheticSave}.cs`: known character/profile facts, no-op equality, exact rune-patch scope, undo/redo, rejection/atomicity, UTF-16, version gates, bounds and sample-dependent skipping are already covered. README records 64 plugin tests and 43 Core tests passing in an earlier implementation round; these were deliberately not rerun here.
- The older reconnaissance in `docs/formats/PPSA03169.md` calls the wrapper unmapped; the current plugin supersedes that uncertainty for the validated prefix/profile scope. Neither document establishes deeper gameplay writes or successful console loading.
- **Rechecked bytes, not merely README:** scratch `verify.py`, run using `python -I`, read ZIP entries directly without extracting or printing account/password ranges. There are two `memory.dat` records, each 28,967,040 bytes, and they are identical primary/backup twins: **one independent snapshot**, one active slot. PlayerGameData is absolute `0xA2FF` / slot-relative `0xA28F`; versions are 150/90; level 12, held runes 1,147, lifetime total 4,427, timer 4,597,996 ms. Attributes 13/13/11/11/16/10/8/9 satisfy the level equation; profile name/level/history mirrors match.
- **New structural evidence:** the source-guided cursor predicts PlayerGameData size `0x1B0` and held inventory at absolute `0xA6A3`. Its common/key counters are 63/2, exactly matching nonempty rows in fixed arrays of 2,688/384 records, each `(handle, quantity, inventoryIndex)` of 12 bytes. These are serialized rows, including internal/unarmed placeholders, not necessarily 65 distinct user-facing possessions. Storage candidate `0x13A5E` has zero common/key counts; a nonempty storage sample is still needed.
- **New semantic cross-checks:** handle resolution yields two Scimitar records (`0x006CF2A0`) and a Riveted Wooden Shield (`0x01CB2310`); direct goods normalization finds Rowa Fruit (`0x400050F0`) ×12, Smithing Stone [1] (`0x40002774`) ×3 and Cracked Pot (`0x4000251C`) ×1. Names come from cited upstream tables, not an in-game screenshot. The map/key row `0x40002198` resolves to Map: Limgrave, West. Ownership/equipped state, every sentinel and all ID classes are not yet validated.
- **Important dependency counterexample:** sampled HP current/max/base are **504/504/476**, FP 88/88/88 and stamina 97/97/97. ClayAmore's Vigor-13 lookup truncates to base HP 476. Therefore copying an editor's unconditional reset-to-base behavior would alter unrelated equipped/effect state. Archetype byte 1 agrees with upstream Warrior mapping and the Scimitar loadout; class identity remains inferred until observed in game.
- `src/SaveToolkit.Sdk/Views/ViewNode.cs`, `Values/{FieldSpec,FieldValue}.cs`, `ISaveDocument.cs`, `BoundSaveDocument.cs`: tabs, lazy sections, searchable tables, descriptions, confidence/warnings, images/assets, typed scalar fields, action parameters and `StructureChanged` already exist. `FieldValue` is scalar, with Int128 integer transport; there is no item-reference type, searchable catalog query, relation between fields, map node, structured operation preview, imported-data context or structural undo token. `EnumOption` has text/description but no icon.
- `src/SaveToolkit.Core/Sessions/DocumentSession.cs` already validates specs and records atomic value batches; undo replays editable primary values and expects derived values to recompute. Non-undoable actions clear history. `BoundSaveDocument` validates individual proposed values before setting them; it does not supply candidate-state dependency validation, and its `SetValues` action helper explicitly bypasses validation. Rich edits need an independently staged plugin transaction, not setters with scattered side effects.
- `Core/Export/WorkspaceExporter.cs` already supports multiple existing `FileOutput`s, reopens an overlay, and mirrors an originally identical backup by default. No new multi-file API is needed for this one-file plugin. `ViewIndex` accumulates published specs/actions; structural rebuild handling must invalidate deleted targets rather than assuming `StructureChanged` alone revokes them.
- `web/src/components/document/TableView.tsx` filters and virtualizes already supplied rows; it does **not** fetch server-side pages. Its cells render fields/text only, so an `ImageNode` cell is blank despite standalone image support in `ViewRenderer.tsx`. `fields/FieldControl.tsx` uses a plain select for enums; `ActionButton.tsx` provides parameters/confirmation but no change preview or multi-row selection. Ordinary text tables and per-character lazy sections are viable immediately.

For complete localized names/descriptions and publisher art, let the user supply a versioned game-data pack produced from their own installation using a separately audited workflow; this does not assert a right to redistribute game assets. Any optional remote provider must be configured and fetched by Core/UI with permission/terms review, caching and offline fallback; **plugins remain network/filesystem-free**. A remote URL or MIT extractor is not itself a licence to embed copyrighted images. Save parsing and unknown-ID display must work with no pack and no network.

### Integrity / crypto

- **PS5 outer layout — verified scope:** sampled allocation is plaintext at the curated character/profile fields, with no PC BND header or per-slot MD5 prefix. [PS writer](https://github.com/ClayAmore/ER-Save-Editor/blob/014107f0ca1cff867b5f7565cb79d6684f9b35df/src/save/playstation/ps_save.rs) concatenates header, common slot payloads and user data directly; [PC slot writer](https://github.com/ClayAmore/ER-Save-Editor/blob/014107f0ca1cff867b5f7565cb79d6684f9b35df/src/save/pc/save_slot.rs) prefixes MD5 over the `0x280000` payload. Do not add PC MD5/encryption to PS5 output. Evidence supports experimental fixed-size writes, not a claim that every unknown region lacks integrity rules.
- **Precise PC-to-PS mapping:** for the inspected PC wrapper, payload slot `i` begins `0x310+i*0x280010`; the sampled PS5 payload begins `0x70+i*0x280000`. Shared slot-relative structures transfer only after a bounded, version-aware walk. There is no one constant whole-file offset adjustment, because each PC slot adds a 16-byte digest and headers/profile wrappers differ. No actual PC/PS4 comparative sample was supplied; transfer beyond verified common fields is inferred.
- **Embedded regulation — new measured result:** [ClayAmore regulation code](https://github.com/ClayAmore/ER-Save-Editor/blob/014107f0ca1cff867b5f7565cb79d6684f9b35df/src/util/regulation.rs) supplies a public game-format AES-256-CBC constant and IV-prefix approach; [UserData11](https://github.com/ClayAmore/ER-Save-Editor/blob/014107f0ca1cff867b5f7565cb79d6684f9b35df/src/save/common/user_data_11.rs) establishes a preceding opaque `0x10` bytes. Independent scratch `verify_extended.py` used that constant internally, without logging it or reading user credentials. At absolute **`0x1960080`**, the first 16 bytes are the IV; decrypting the subsequent blocks yields **DCX/DFLT**. Bounded zlib decompression completed at its declared size: **1,859,344 compressed bytes → 37,745,424 bytes**, beginning `BND4`; UTF-16 table strings include EquipParamGoods, CharaInitParam and BonfireWarpParam. This proves a workable decode path/signature and table-name presence, not complete BND/PARAM validity, all caps, FMG text or a safe regulation writer.
- Keep this allocation **byte-identical** even when reading its parameters. Parse runtime sizes/header versions rather than copying upstream's historical hard-coded regulation slice length. Set bounded decryption/decompression/archive/row budgets; the observed 37.7 MB expands well beyond the encrypted payload. No need for a new user-supplied secret key for this measured path. Current game updates, other compression variants and malformed/overwritten regulation remain unknown; provide an external matching pack fallback without silently changing the save's regulation.
- **Event storage — partial:** independently following the inspected common-slot sequence predicts a `0x1BF99F`-byte flag region starting absolute `0x36600`, after bounded projectile/region/acquisition structures. Using upstream byte/bit mappings gives 76100/76101 set and 76102/76103 clear; upstream grace names are Church of Elleh/The First Step/Stormhill Shack/Artist's Shack. These are plausible byte states, **not independently observed in-game progress**, and neither the start offset nor block lookup is universal across versions. No flags were written. Current pool semantics and quest dependencies need separate controlled experiments.
- **Unknown integrity/dependencies:** semantic consistency across equipment mirrors, acquired-item tracking, container capacities, maximum-ever weapon matchmaking tier, quest families, DLC blessings/NG+ and any unknown internal summaries. Successful self-reparse only proves the checks implemented by our parser; console reload/resave is required to detect missing invariants. PS5 outer save mounting/signing remains the existing save-manager workflow, outside this decrypted plugin.

## Vision

- **Characters:** ten-slot chooser with active/inactive status; localized name, starting class, level, runes and play time; base/effective HP/FP/stamina explicitly separated. A respec form validates class minima, derives level, previews all related changes and shows relevant softcaps as guidance distinct from hard limits. Name editing updates both live and menu copies with strict UTF-16 validation.
- **Inventory / Storage:** categorized, searchable lists or icon grids with stable instance identity, quantity, per-item held/stored caps, ownership/equipped markers, upgrade/affinity and provenance. Details show descriptions, requirements, raw IDs and “not mapped” fallbacks. Start with existing safe stacks; later add selected transfer/remove/add operations with capacity preflight. A “refill selected ordinary materials to legal cap” action excludes flasks, containers, key/story and unknown items.
- **Equipment / Builds:** six armament slots, ammunition, armour, talismans, spells, quick items, pouch, Physick and AoW links. Pick existing compatible instances first; display requirements, enabled slots and base/effective stat consequences. Local build presets preview differences and skips; an incomplete build never silently creates unknown or unavailable content.
- **Progress / World:** graces, map fragments, bosses, selected collectibles and quest milestones grouped by region/layer, with DLC/NG+ coverage explicit. A read-only map highlights sourced locations and save-observed status. “Currently owned”, “ever acquired”, “flag observed”, “manual step” and “unknown” remain distinct; a missing item is not automatically an uncollected pickup. Only individually validated allowlisted unlock actions become writable later.
- **Review / Raw:** semantic before/after review, dependency explanations, one-step undo for a whole operation, backup/export information and preserved bounded hex. Confidence and dataset compatibility remain visible. No feature promises ban avoidance, complete quests from arbitrary flag toggles, or universal cross-region/patch compatibility.

## Phased plan

Sizes are rough engineering packages: S = a few focused days, M = roughly 1–2 weeks, L = multiple weeks plus external validation waits. These are planning estimates, not commitments. Phase 1 can begin without new SDK/UI features; later gates are per capability, so a blocked quest writer does not hold up a read-only inventory release.

**Phase 1 — bounded semantic reader and evidence corpus (M).** Goal: useful named read-only inventory/equipment facts on the known layout without broadening writes.

- [ ] Introduce composed bounded readers/range descriptors for GaItem, PlayerGameData, equipment, held/storage arrays and candidate event structures; retain the original allocation as the source of truth. Avoid a monolithic reserializer and keep normal C# files preferably <300 LOC, never >500.
- [ ] Resolve handles through the GaItem map and distinguish direct goods/talisman/AoW IDs from instance IDs; preserve duplicates, unknown categories, empty sentinels and internal placeholders. Stable IDs include character, container and record/instance identity, not item name or list position alone.
- [ ] Publish held/storage tables by character/category with raw fallback and confidence; initially use a reviewed minimal names crosswalk and existing SDK nodes. Show vitals/class/equipment as inferred until independently confirmed.
- [ ] Reproduce sample offsets/counts/names in sample-skipping tests and add synthetic edge cases for unknown IDs, corrupt variable counts and missing references. Record the source revision and evidence level for every mapping.

Evidence needed: ELDENRING-R1, ELDENRING-R2, ELDENRING-R3, ELDENRING-R10. **Risk:** mistaking valid internal rows for inventory or conflating ID spaces. Exit: no-op equality and honest read-only views, not new editable fields.

**Phase 2 — versioned reference data, legal limits and rich browsing (L).** Goal: trustworthy names/categories/limits and optional descriptions/icons for base game and verified DLC versions.

- [ ] Decode regulation read-only with bounded AES/DCX/BND/PARAM readers using approved permissive code or independently implemented format facts. Validate actual headers, entry bounds, row layouts and schema versions; preserve the encrypted bytes verbatim.
- [ ] Generate canonical item/category/upgrade/AoW/class/grace records with provenance and versioned caps. Verify param limits against observed carry/storage behavior; distinguish technical capacity from permitted quantity and containers/shared capacity.
- [ ] Define/import normalized packs containing language, game/regulation/schema versions, coverage, content hashes, licences and asset manifests. Reject ambiguous mismatches; use placeholders and raw IDs for missing data.
- [ ] Improve table cells/details and catalog search, filters and icon loading using shared UI capabilities. Do not require a map or full image set to release textual inventory.

Evidence needed: ELDENRING-R3–R7, ELDENRING-R11, matching regulation/FMG/icon exports supplied locally. **Risk:** unlicensed data, stale DLC rows, decompression cost or treating schema display maxima as legal caps. Exit: all writable candidates have approved identity and limits; unknowns remain read-only.

**Phase 3 — existing-value edits and coupled character changes (M–L).** Goal: small, reversible edits with all dependent values understood.

- [ ] First enable existing ordinary consumable/material quantities only for confirmed containers/IDs/caps; initially reject zero if deleting an entry requires structural updates. Preserve IDs/handles/counts/acquisition/equipment state and reject container-managed/story/unknown entries.
- [ ] Enable live/menu name edits with explicit encoding/terminator/surrogate handling, both mirrors updated and unrelated trailing bytes preserved. Add non-ASCII before/after fixtures.
- [ ] Stage class-aware attribute changes as a whole respec transaction; derive level and profile level, establish base-stat rounding, and preserve/recompute affected current/effective vitals according to observed rules. Keep class identity read-only initially. Do not port an unconditional HP/FP/stamina reset.
- [ ] Keep held-rune/history guard unchanged until earning/spending/loss experiments establish lifetime semantics; only then offer an atomic linked increase with both history mirrors updated and checked for overflow.
- [ ] Add previewed “refill selected safe stacks” and supported build-stat presets. Report every primary/derived `ValueChange`; validate candidate state before swapping bytes; prove failure leaves bytes/history unchanged and undo works with unopened lazy sections.

Evidence needed: ELDENRING-R1/R2/R3/R8/R9/R10/R12; game reload/resave per edit family. **Risk:** modifier-dependent vitals and historical totals. Exit: finite allowlist of validated fixed-size edits, not a generic “max everything”.

**Phase 4 — existing equipment, upgrades and loadout presets (L).** Goal: manage owned gear without creating/removing objects.

- [ ] Read/validate the relationship between EquipData, ChrAsm, ChrAsm2, EquippedItems, quick/pouch/spell records, GaItem AoW handle and inventory index. Identify active hand slots, empty/unarmed representations and all required mirrors.
- [ ] Allow equipping existing compatible instances, respecting talisman/memory slot unlocks, category/ownership and duplicate restrictions. Test disallowed and valid combinations, weapons carried twice, spells and pouch items.
- [ ] Add upgrades/affinities/AoW swaps only when matching regulation supports them; model normal/somber upgrade paths and maximum-ever matchmaking tier. Preserve historical tier when reducing/removing gear unless controlled evidence establishes another rule.
- [ ] Provide local versioned loadout presets with explicit existing-item matching, compatibility/slot preflight and a semantic preview. Compute damage/load/defence estimates only when all required params/effects are covered; otherwise label unavailable or approximate.

Evidence needed: ELDENRING-R2/R3/R9/R12/R14, multiple same-base gear instances and controlled upgrade/equip pairs. **Risk:** stale references, incompatible ashes, matchmaking history and stat modifiers. Exit: tested owned-instance operations; no hidden item creation.

**Phase 5 — progress, collectibles and maps; limited unlocks (L).** Goal: a useful read-only progress dashboard and optional geographically accurate map.

- [ ] Parse versioned event blocks with the actual block lookup and bit order, plus acquired-item history and relevant dedicated progress structures. Cross-check grace/boss/map observations against controlled saves; treat summoning pools as a separate version-sensitive mapping.
- [ ] Build named regional boss/grace/fragment/collectible lists and a quest milestone graph; retain ambiguous/manual steps outside save state. Distinguish NG+ resets, mutually exclusive paths, consumed/sold items and changed world layers.
- [ ] Add sourced map coordinates/layers, icon placeholders and accessible synchronized list selection. Obtain/derive map art separately; region/entity/event/text IDs must be explicitly joined.
- [ ] Consider individual allowlisted grace/map unlock transactions only after documented game behavior and prerequisites. Boss revival, quest completion/repair, mass flag clears and NPC resurrection stay disabled until separately proven, even if another editor offers them.

Evidence needed: ELDENRING-R2/R3/R13/R15/R16 and human-controlled world transitions. **Risk:** softlocks, misleading completion claims, spoilers and unavailable art. Exit: independently checked statuses; only validated unlocks, no arbitrary flag editor.

**Phase 6 — structural inventory and complete build application (L, gated).** Goal: add/remove/transfer records without corruption or lost undo history.

- [ ] Establish free-record/handle allocation, GaItem map growth/compaction within fixed slot size, distinct counts, next equipment/acquisition indices, acquisition-history updates and cleanup of dependent equipment references. Preflight every relevant array and reject saturation atomically.
- [ ] Implement transfer/merge/split/remove before arbitrary creation; prove whether instances/handles move or duplicate. Support a small allowed item set first, excluding game-managed containers, cut content and unknown DLC entries.
- [ ] Add/remove creates stable identities and invalidates deleted field/action targets. Use framework-supported operation mementos or opaque reversible deltas; exact undo must restore every affected byte and prior references across lazy-view rebuilds.
- [ ] Build presets may create only approved missing items after previewing counts, capacity, compatibility and skips; add no “all items” preset until the identity/capacity model is proven at realistic scale.

Evidence needed: ELDENRING-R1/R2/R3/R12/R17–R19 and full/near-full inventory fixtures. **Risk:** variable map length shifts downstream data, orphaned references and incomplete undo. Exit: structural actions remain disabled until exact rollback/reload tests pass; this phase is not needed to ship phases 1–5's reader/value edits.

## Open questions & risks

- One early-game snapshot cannot establish all layout variants, storage semantics, DLC structures, high-level/cap behavior or quest state. Region IDs identify a title, not interchangeable bytes; internal slot/profile versions are not app-version strings.
- Is the current “lifetime rune total” invariant complete after rune loss/recovery, NG+, imported characters or earlier editors? Conflicting parser labels and updater behavior require experiments; retain the conservative guard meanwhile.
- How are current/effective/base HP/FP/stamina, equipment effects, Great Runes and temporary buffs persisted/recomputed across a load? The measured HP difference disproves the assumption that all three values should always equal the base table.
- Which serialized rows are engine-required unarmed/placeholders, and which duplicates are legal? Empty/sentinel rules and per-array counts must be proved before filtering, compacting, merging or allocating entries.
- Can regulation always be read from the save, and what does the game tolerate when another editor overwrites it? We confirmed one AES/DCX payload, not a universal fixed ciphertext length or a writer. A matching user pack may be essential for later/modified saves.
- How do weapon upgrades, Ashes of War and acquisition history affect the maximum-ever matchmaking tier? Inventory removal must not reset history without evidence. No claim of online acceptance follows from normal ranges or another tool's “safe” mode.
- Quest state is a graph with alternative/one-time/resetting milestones, not a collection of independent checkboxes. Separate boss defeat, reward acquisition, NPC lifecycle, world transformation and platform trophies. Do not promise repair/100% tracking where the save lacks sufficient evidence.
- Post-1.12 pool changes reported by the maintained fork need direct source/differential verification; a grace event mapping is not automatically a summoning-pool mapping. Map assets/coordinates and actual event state need independent joins.
- Root licence badges do not settle vendor-code, table, translated-wiki, FMG-text or game-art rights. Unknown licences are not permission; GPL/restricted sources remain references unless an explicitly reviewed route is chosen. User-supplied data solves transport, not redistribution rights.
- UI-rich features should not block a valuable first release: lazy textual inventory/progress and safe existing-value edits fit today's protocol. Structural item creation and broad quest/world edits are the highest-risk tail and should remain independently gated.
- Scratch reproduction files are under `<ps5plans>/scratch/EldenRing/`: `verify.py`, `verify_extended.py`, `final_probes.py`, `sample-findings.json`, `extended-findings.json`, and pinned source/catalog files. Only independently written probes were executed with `python -I`; downloaded implementations were read, not run. This deliverable is planning only, not a patch or new validation claim.
